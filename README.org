#+title: Star Vector
#+description: Exact vector storage and search for validated StarIntel documents.

* Star Vector

Star Vector is a small persistent vector store implemented in Nim. Every vector
is stored with a StarIntel document validated against the repository-pinned
StarIntel 0.10.1 schema. The same implementation is available through:

- the =star_vector= Nim module;
- the =star-vector= command-line client;
- a stable C ABI in =include/star_vector.h=; and
- a Common Lisp client built with CFFI and CFFI-Grovel.

The initial backend performs exact exhaustive search. It supports cosine
similarity, dot product, Euclidean distance, and Manhattan distance. Similarity
scores sort high-to-low; distances sort low-to-high; equal scores are ordered by
document ID.

* Build and test

#+begin_src sh
nix develop
nimble test
nix flake check
nix build
#+end_src

The flake installs the CLI, shared library, C header, Nim sources, and Common
Lisp ASDF system. Run the packaged CLI with =nix run=.

* Command-line client

Vectors are comma-separated decimal values and every operation states the fixed
store dimension. New persistent stores are Tek9/LMDB directories with transactional writes
coordinated across processes. Existing JSON files are read-only legacy snapshots.

#+begin_src sh
star-vector init vectors.tek9 3
star-vector upsert vectors.tek9 3 document.json 1,0,0
star-vector get vectors.tek9 3 doc:example
star-vector search vectors.tek9 3 cosine 10 1,0,0
star-vector delete vectors.tek9 3 doc:example
#+end_src

=document.json= must contain a supported canonical StarIntel document. At
minimum, a generic document has fields like:

#+begin_src json
{
  "id": "doc:example",
  "dataset": "examples",
  "dtype": "document",
  "schemaVersion": "0.10.1"
}
#+end_src

* Nim library

#+begin_src nim
import star_vector

let store = openVectorStore("vectors.tek9", 3)
defer: store.close()

store.upsertDocument(document, @[1.0'f32, 0.0'f32, 0.0'f32])
let matches = store.search(@[1.0'f32, 0.0'f32, 0.0'f32], vmCosine, 10)
#+end_src

* C ABI

Include =star_vector.h= and link =libstar_vector.so=. Store handles are opaque.
Build the shared library with =-d:noSignalHandler -d:useMalloc= (the flake does
this). It preserves the host runtime's signal handlers and uses the process
allocator so foreign threads need no Nim allocator registration. Pipe writes
mask SIGPIPE only on the calling thread. Independent handles may be used
concurrently. Serialize calls on each individual handle, including close.
Schema validation is serialized internally to protect shared schema references.
Strings returned through =sv_get_document= and =sv_search_json= belong to the
caller and must be released with =sv_string_free=. The pointer returned by
=sv_last_error= remains owned by the library and is valid until the next call on
that handle.

#+begin_src c
sv_store_t store = NULL;
sv_open("vectors.tek9", 3, &store);
sv_upsert_document(store, document_json, vector, 3);
sv_search_json(store, query, 3, SV_METRIC_COSINE, 10, &results_json);
sv_string_free(results_json);
sv_close(store);
#+end_src

* Common Lisp client

The ASDF system is =star-vector=. It Grovels the installed C header so sizes and
constants come from the ABI rather than duplicated Lisp declarations. Point
=STAR_VECTOR_LIBRARY= at the shared library when it is not in the platform
loader path.

#+begin_src lisp
(asdf:load-system "star-vector")

(star-vector:with-store (store "vectors.tek9" 3)
  (star-vector:upsert-document store document-json #(1.0 0.0 0.0))
  (star-vector:search store #(1.0 0.0 0.0) :cosine 10))
#+end_src

The search result is JSON so the ABI remains language-neutral and document
payloads retain their canonical StarIntel representation.

#+begin_src sh

Refreshing the pin requires an exact canonical checkout and the explicit
=--canonical-root=, =--canonical-repository=, =--canonical-commit=, and

* Tek9 storage and explicit legacy migration

Persistent paths now name dedicated Tek9/LMDB directories. The flake pins the
producer =lost-rob0t/tek9@e6d1cb86a2e268a894eae3acae9617238b2adcff= and consumes
=packages.<system>.tek9=. An application adapter imports the ASDF library in a
private SBCL worker per persistent handle; Nim communicates over local pipes.
This is a process boundary, not an in-process Nim import. There is no listening
service. No Tek9 implementation is copied into Star Vector. Packaged binaries
embed the immutable worker executable path. Source builds use
=STAR_VECTOR_TEK9_WORKER= (set by =nix develop=).

The CLI, C ABI and Lisp client retain their operation signatures and metric
ordering. Acknowledged mutations use Tek9 =:full= transactions; LMDB coordinates
writers across handles/processes. Each search streams a single read snapshot
through a top-k heap. Scores retain the original float32-input/float64-arithmetic
contract, with document-ID ties. Transient empty-path stores stay in memory.
512-byte canonical IDs use an isolated hashed storage key, with full-ID collision
checks before replacement or deletion. Such a collision fails without overwriting.

Old =star-vector/1= JSON files remain readable and are never rewritten on open,
flush or close. Writes to them fail with a migration instruction. To migrate:

#+begin_src sh
star-vector migrate old-vectors.json new-tek9-directory 384
# Optional maximum records in this invocation, for checkpointed progress:
star-vector migrate old-vectors.json new-tek9-directory 384 1000
# Repeat the same source and destination to resume and verify readback.
#+end_src

The migration validates the complete legacy snapshot before touching the target.
It retains the original file, binds progress to a SHA-1 source-byte fingerprint
(change detection, not authenticity), dimensions and count, and commits bounded
batches together with their checkpoints. Batches target 128 records / 1 MiB;
one larger row is permitted to preserve the existing document contract. An
incomplete target rejects ordinary opens. Competing migrators are fenced by the
expected checkpoint. Publication follows full record/count readback and a second
source fingerprint check. An existing unrelated or unmarked Tek9 store is refused.
Existing stores are probed through read-only, non-creating LMDB calls before
Tek9 opens or prepares any named databases. A lock on the directory inode
coordinates first creation without adding a lock file to the destination.
A crash before the initial header commit may leave an unmarked directory; choose
a new destination rather than deleting or adopting unknown data automatically.

** Measured limits and validation

- Exact search still visits all records and validates each decoded document.
  Work is O(N*d + N*log(k)); retained results are O(k), plus the largest record.
  It is not an approximate index. Long snapshots can pin LMDB pages.
- SBCL startup, JSON encoding/decoding, IPC, runtime heaps and mapped pages are
  real costs. One worker belongs to each persistent handle. Keep handles open
  across operations; migration batches do not launch a process per record.
- The producer reserves a fixed 16 GiB virtual map by default; automatic growth
  is not provided. Map-full failures abort the transaction and surface as errors.
- Legacy loading/migration still parse the whole JSON snapshot in memory. There
  is no claim of bounded-memory legacy import, constant total RSS, or power-loss
  verification from a process-kill test.
- EOF closes the worker. Normal close waits/reaps it; failed scans terminate it
  so unread rows cannot corrupt subsequent replies. Worker loss fails the handle;
  reopen and inspect state rather than retrying an ambiguous mutation blindly.
  C operations return I/O errors and Lisp raises =star-vector-error=. Do not race
  close with calls on the same C handle; caller ownership of handle lifetime remains.

=tests/storage_integration.py= covers synthetic cross-language reopen, concurrent
handles/processes, producer rollback, killed-worker errors, parent-exit cleanup,
512-byte IDs, source preservation, interrupted/resumed migration and readback.
=tests/test_search_reference.nim= compares all four metrics with an independent
exhaustive reference. =benchmarks/storage_benchmark.py= reports separate native
Tek9 scans, worker bridge scans, Nim searches, no-op IPC, startup/reopen, batch
writes and parent/worker RSS at 1k/10k/50k synthetic rows. RSS includes mapped
pages and runtime heaps. Native CI exports JSON artifacts; no benchmark threshold
or production-readiness claim is implied by these sample sizes.

** Matched memory profiling

Build the synthetic baseline/candidate comparison with:

#+begin_src sh
nix build .#memory-profile --no-update-lock-file
cat result/memory-profile.json
#+end_src

The validation-only =memory-baseline= input pins merged revision =0247e406=.
Both variants import the same Tek9 library and use the same Nim/SBCL toolchain.
The benchmark records separate parent/worker RSS, PSS, anonymous memory,
LMDB/core mappings, cumulative Lisp allocations, sampled dynamic-space peaks,
ten consecutive searches, reopen and three simultaneous handles. Explicit full-GC
checkpoints estimate live dynamic space; they do not represent all runtime/code
memory or imply the OS returned freed pages. Only benchmark images load these
hooks. Six separate uninstrumented timing samples per variant use ABBA order.
The normal worker has no profiling hooks or forced-GC policy.

Scan responses stream JSON escaping directly to the pipe. They retain the same
wire fields and stored record strings, including pretty JSON and Unicode, while
avoiding full-size escaped-string and response-string copies. The producer still
decodes each record and Nim still parses and validates it. No store rewrite,
new storage format, or heap-limit reduction is involved. Small =k= bounds retained
results; large individual records, SBCL startup/core memory, mapped LMDB pages
and one worker per handle remain real costs.

The package compiles dependency FASLs once and launches the worker by loading
those immutable files into SBCL. This avoids custom saved-image fragmentation.
It trades additional startup work for predictable repeated-search residency;
keep handles open across operations. Total RSS/PSS across repeated searches,
not only live object bytes, must substantiate a memory improvement.

At =2ebd35f=, native PR run =38118774269= measured 50k rows with ten searches:
worker RSS after the tenth search fell from 579 to 339 MiB on x86 and from
496 to 336 MiB on ARM; first-scan allocation fell 66% / 71%. Parent RSS stayed
about 31 / 33 MiB. This is a sustained-search tradeoff: idle worker RSS rose
from about 84 / 78 to 140 / 138 MiB, and instrumented open time rose from
54 / 54 ms to 935 / 1098 ms. Small or short-lived workloads may cost more.
The design notes record PSS, live heap, latency, artifacts and measurement limits.
