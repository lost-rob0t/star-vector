* Verified Facts

StarVector's four exact metrics remain correct against an independent scalar
oracle, including reopened Tek9. Reusing the query norm and the candidate
norm removes redundant cosine arithmetic without changing result IDs or
float64 scores. It improves the transient path, but does not establish a
persistent speedup. The current durable search still spends substantial time
streaming, parsing and validating full records through the producer worker.

The main matrix completed 57 cells, recorded one Qdrant readiness failure,
and explicitly skipped three expensive Tek9 cells. It covers a 10k/50k/100k/1m
ladder at 128 dimensions, a 50k dimension sweep at 384/768/1536, and a 100k
uniform-random stress corpus. A separate larger Flat cell and matched ABBA
checks supplement the matrix. These are synthetic execution results, not a
tested-billion or production-readiness claim.

The production engine still exposes exact cosine, dot, Euclidean and
Manhattan only. Faiss Flat/HNSW/IVF/PQ and Qdrant are real external benchmark
implementations, not newly exposed StarVector methods. Tek9 remains the
imported authoritative producer. No storage format, migration behavior,
canonical schema pin, CLI command or ABI changed.

* Database/API results and durability differences

SQLite is embedded, StarVector uses C ABI plus Tek9 worker JSON, and Qdrant
uses loopback HTTP JSON. Every database query returns document payloads.
These end-to-end measurements include different transports and validation
paths; do not attribute the Qdrant HTTP latency to its ANN kernel or compare
it directly with Faiss library latency. No gRPC comparison was executed.

|---------------+----------------+---------------+---------+-----------+-------------|

| StarVector/Tek9 50k x 128 | 89.27 | 4493.68 | 3 | 1.0 | 392.36 |

StarVector ingress validates each document and commits one row per durable
C ABI call. SQLite uses 128-row WAL/FULL transactions; Qdrant uses 128-point
wait=true requests. Those transaction sizes and durability acknowledgments
are unequal and explicit. Ingest rates are not an apples-to-apples storage
kernel contest. SQLite/Qdrant do not run the canonical Nim schema validator.
Build timing includes normalization/training/add for Faiss and ingestion plus
index readiness for Qdrant. A warm scan follows build and limited warmup.

Qdrant's million-row attempt lasted 666.38 seconds. At the 300-second
readiness deadline it reported 1m points and 1m indexed vectors, but yellow
optimizer status. Cleanup succeeded. The result is a readiness-budget failure,
not evidence that Qdrant cannot store or search 1m vectors. No queries were
measured for that cell and no missing timings are inferred from smaller cells.

The runner skipped Tek9 1m x 128, 50k x 768 and 50k x 1536 because conservative
linear scheduling estimates from observed smaller cells exceeded its 1200 s
per-cell budget. These are unexecuted cells, not OOM failures or measured
maximum capacities. The complete dimension sweep still ran for Faiss,
StarVector transient, SQLite-vec and Qdrant. Larger real embeddings and a
billion active rows remain untested.

* Filtering, concurrent reads and snapshot/write behavior

At 100k x 128, IVF-flat's unfiltered recall was 1.0 with nprobe=4, but recall
fell to 0.752 at 1% eligibility and 0.119 at 0.1%. The eligible-ID selector
was applied inside IVF search; these misses are not a postfilter artifact.
Qdrant and SQLite reached full recall in the measured 50k filter cells.
The harness did not exercise native filters for Faiss Flat/HNSW; their
unsupported rows do not imply those libraries lack such facilities.
StarVector itself has no predicate API yet. Empty eligible sets return empty
results in supported measured paths. No invalid/duplicate/ineligible IDs were
reported by completed cells.

The 50k Tek9 reopen took 1.022 s; its first query took 4.472 s and matched
the oracle. Four independent readers executed 12 queries with full recall,
median query latency 10.760 s and wall throughput 0.349 queries/s, including
handle startup. This small concurrency sample does not support a p99 claim.
Qdrant process restart and SQLite connection reopen also passed their count/
query checks. All of these retain OS cache; true cold-cache eviction was not
verified and no true-cold result is claimed.

Holding a 50k-row producer read snapshot while overwriting 1000 rows preserved
the original revision for every streamed record. Snapshot duration was
4.786 s. LMDB file size grew by 36,757,504 bytes while the reader was pinned;
the same subsequent overwrite count after release added zero file bytes.
Pinned-write p50/p99 were 1.559/3.914 ms versus 1.226/2.559 ms after release.
This measures producer snapshot/write overlap and page reuse, not query
scoring latency during a continuously varying arrival-rate workload.

The ordinary 50k mutation cells updated and deleted 100 rows each. Tek9 took
0.136/0.097 s, SQLite 0.114/0.079 s and Qdrant 0.192/0.159 s for update/delete
totals. SQLite verified the reduced count after reconnect. Qdrant's mutation
count check is separate from its earlier process-restart test. Existing native
integration checks cover worker loss, in-flight transaction crash rollback,
reopen, concurrent clients, migration restart and source/readback preservation.

* Memory, disk and write accounting

RSS/PSS and anonymous/file-backed residency are sampled every 100 ms across
the driver and live children. Reported peaks are observed samples, not proven
maximum bounds. RSS can double-count shared pages; PSS apportions them.
File-backed RSS can include anonymous COW pages, so those classifications
must not be added together. The Faiss driver retains normalization staging
and the source memory map, and PQ retains originals for reranking; process
memory is not the same as serialized index size.

| Cell | Peak summed RSS MiB | Peak PSS MiB | Anonymous MiB | File RSS MiB |
|------+---------------------+--------------+---------------+--------------|
| Faiss Flat 1m x 128 | 1516.8 | 1514.0 | 1004.1 | 514.9 |
| Faiss HNSW 1m x 128 | 1673.9 | 1671.1 | 1160.9 | 515.2 |
| Faiss IVF-PQ 1m x 128 | 1095.6 | 1092.8 | 582.6 | 516.9 |
| StarVector transient 1m x 128 | 6606.8 | 6604.0 | 6108.8 | 499.6 |
| SQLite-vec 1m x 128 | 615.2 | 612.4 | 116.5 | 500.4 |
| StarVector/Tek9 100k x 128 | 995.3 | 991.7 | 128.0 | 870.7 |

The 50k Tek9 lifecycle cell additionally opens four readers: its summed peak
RSS was 2615.8 MiB while peak PSS was 949.2 MiB. Do not compare that peak
with a one-handle row as if the workload were identical. A large resident LMDB
mapping does not demonstrate whole-store heap hydration.

The raw evidence retains per-process Linux I/O counters. For the 50k lifecycle
cells, observed kernel write_bytes were about 2.540 GB across Tek9 workers,
0.320 GB for SQLite and 0.567 GB across Qdrant server processes. The Tek9 cell
also includes 2000 extra snapshot-experiment overwrites. These counters are
sampled and include WAL/page maintenance and multiple phases, not just ingest.
They are not device-level write amplification or fsync equivalence. Parent
counters can inherit waited-child I/O: summing parent and child maxima would
double-count. On-disk bytes are logical file lengths, including WAL where
present, not necessarily allocated filesystem blocks. These constraints
prevent claiming a directly comparable physical write-amplification factor.

* Inference

Process-isolated ABBA comparisons used 100 independently checked queries per
pass. Baseline/candidate medians were 29.693/28.110 versus 18.171/18.871 ms
at 50k x 128, and 248.388/256.504 versus 148.759/142.314 ms at 50k x 1536.
The averages of the two process medians improved about 36% and 42%. Every
pass produced the same ID-and-score digest. The 10k persistent ABBA medians
varied from 839 to 1376 ms and did not establish a persistent improvement.

Retain this narrow exact optimization and the independent contract tests.
For meaningful persistent acceleration, the next slice needs a producer-backed
consistent snapshot/change boundary, compact candidate data and generation-
qualified exact reranking. Test HNSW/IVF choices and eligible-set fallback on
actual model embeddings before selecting an index. The current PQ settings
are not an acceptable substitute merely because the code bytes are smaller.

The [[file:../../design/star-vector/tiered-search.org][active/history design]] separates logical validity, latest/as-of revisions
and tombstones from physical placement. It specifies compatibility keys,
rebuildable generation manifests and Tek9 authority. Billion float32 vectors
alone need 512 GB at 128 dimensions or 6.144 TB at 1536, before documents,
indexes, history or replication. Shards, history APIs, DiskANN, distributed
recovery and ANN publication are proposed follow-up work, not implemented
features in this PR.

* Contradictions

Reducing repeated cosine arithmetic did not establish a persistent latency
gain: producer transport and full-record processing still dominate that path.
The smallest tested PQ index had substantially worse recall, so code size
alone does not select a useful method. High unfiltered recall did not carry
over to selective IVF queries. Qdrant reported a million indexed vectors
while its optimizer remained yellow; index count alone did not satisfy the
experiment's readiness criterion. These observations are retained rather
than resolved by relabeling failed or unexecuted cells as successes.

* Unresolved Questions

- Which real StarIntel embedding models, revision volumes and filter skews
  should set acceptance targets for a production candidate provider?
- What accuracy, index size and latency result from predicate-aware tuning,
  larger candidate budgets, disk-oriented methods and gRPC transport?
- How long does the million-row Qdrant optimizer need to reach the chosen
  readiness state, and how does it perform after that point?
- What are verified cold-cache costs and device-level write amplification
  under matched transaction sizes and durability requirements?
- What producer snapshot/change protocol and shard-generation lifecycle meet
  active/history consistency requirements under crashes and concurrent updates?
- What multi-host hardware, capacity and throughput are required for a billion
  active vectors plus retained history? This machine cannot establish that.
